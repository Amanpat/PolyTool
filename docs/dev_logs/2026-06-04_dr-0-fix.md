## What the review found (the spec) and what changed

### Blocker 1 — Unbounded shutdown / tick not bounded to grace
`stop_discovery_scheduler(wait=True)` could wait past Docker's stop grace; a
`queue_drain` tick had no stop-time budget (scan HTTP default 120s/request × retries).

Fixes:
- **Cooperative stop between wallets.** `ScanWorker.run(should_stop=...)` checks a
  stop callback BEFORE leasing each wallet, so once stopping it never starts a new
  wallet (`packages/polymarket/discovery/scan_worker.py`). The in-flight wallet is
  allowed to finish its own bounded scan; it is never force-killed. It is protected
  by per-wallet all-or-nothing ingest + lease expiry if SIGKILL still lands.
- **Bounded, testable shutdown core.** New `run_scheduler_blocking(...)` in
  `packages/research/scheduling/discovery_scheduler.py` traps SIGINT/SIGTERM (+
  SIGBREAK on Windows), calls `request_drain_stop()` (cooperative cancel) THEN
  releases the wait, and calls `stop_discovery_scheduler(scheduler, wait=False)` so
  shutdown never blocks unbounded. The CLI `_scheduler_start` now delegates to it.
- **Drain-scoped request timeout.** `_job_run_queue_drain` sets
  `SCAN_HTTP_TIMEOUT_SECONDS` from `queue_drain.request_timeout_seconds` (default
  **15s**, config-driven) so an in-flight wallet's scan can't run for minutes. This
  is set in the scheduler process only; the foreground `wallet-scan` (DR-2) process
  keeps the 120s default (verified: `wallet_scan.py` never sets it).
- **Compose grace.** `discovery-scheduler` now has `stop_grace_period: 60s`
  (`docker-compose.yml`), comfortably above the 15s per-request bound.

### Blocker 2 — Live lock expired at 30 minutes
Old `_is_stale()` treated any lock older than `stale_seconds` (or bare-PID-dead) as
stale, so after 30 min a manual worker could reclaim the LIVE scheduler lock →
double drain.

Fix: **heartbeat (mtime) liveness.** `worker_lock.py` rewritten. The holder runs a
daemon thread that bumps the lock file mtime every `heartbeat_interval` (60s).
Staleness = `now - mtime > max(30s, 3×interval)` (=180s). A live holder that keeps
beating is NEVER stale regardless of `acquired_at` age. Bare-PID liveness is retired
(also closes the PID-reuse / Windows-always-alive should-fix).

### Blocker 3 — Non-atomic acquisition
Old code did check-then-`write_text()` (TOCTOU). Fix: `os.open(path,
O_CREAT|O_EXCL|O_WRONLY)` — the kernel guarantees exactly one creator. On contention
we read the existing lock and reclaim ONLY if heartbeat-stale (one retry for the
stale→race), else refuse.

### Blocker 4 — Fail-open
Old code logged a warning and ran unlocked if the lock couldn't be written. Fix:
**fail closed.** Any failure other than "a live holder has it" raises
`WorkerLockError`; both CLI call sites catch it and return non-zero. There is no
unlocked-drain path anywhere.

### Should-fixes
- **`--force` can no longer stomp a live holder.** `force` only reclaims a
  heartbeat-stale lock (the same thing normal acquisition reclaims); against a live
  heartbeat it raises `WorkerLockHeld`. "Two drainers impossible" holds even with
  `--force`.
- **Broad `try/finally` release.** Both `_run_worker` and `_scheduler_start` wrap
  acquire→run→shutdown in `try/finally: lock.release()`, so any startup/runtime
  exception frees the lock (stale-reclaim is now only a crash backstop).
- **Shutdown failure propagates.** `run_scheduler_blocking` returns `1` when
  `stop_discovery_scheduler` reports failure; `_scheduler_start` returns that code
  and prints the clean message ONLY on `0`.
